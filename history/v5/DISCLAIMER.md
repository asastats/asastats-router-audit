# Security Audit Disclaimer & Methodology Scope

**Audit Version:** v5  
**Target Contract:** ASA Stats Smart Router (`router/contracts/router_app.py`)  
**Deployment References:** Mainnet App ID `3688554446` | Testnet App ID `770123816`  
**Date:** 2026-08-29  

---

## 1. Scope & Boundaries

This security audit covers:
1. The **on-chain PyTEAL / PuyaPy smart contract** source code in `router/contracts/router_app.py`.
2. The compiled **TEAL approval and clear-state bytecode** generated by PuyaPy v5.9.0 (`Router.approval.teal`, `Router.clear.teal`).
3. The **off-chain group assembly, execution math, and quoting logic** in `router/*.py` as it interacts with on-chain protocol constraints.
4. The **dust sweep portfolio classification and transaction construction** logic in `router/sweep.py`.

### Out-of-Scope Items
- The underlying smart contracts of external AMMs (Tinyman v2, Pact, STAMM, AlgoFi). These protocols are assumed to behave according to their published bytecode and audits.
- The physical host security, private key management, and custody infrastructure of the quote signer and administrator key holders.
- Algorand consensus-level protocol bugs (e.g., core AVM consensus failure).

---

## 2. Methodology & Tooling

The audit combines:
- **Exhaustive Manual Review:** Line-by-line review of state transitions, inner transaction construction, ARC-4 ABI compliance, and error branches.
- **Formal & Semi-Formal Invariant Verification:** Verification of value conservation, non-reentrancy, balance delta measurement, and group integrity.
- **Automated Static Analysis:** Crytic Tealer analyzer runs across all detectors with formal dataflow proofs for path-enumerated invariants.
- **Vulnerability Pattern Scanning:** Complete audit against the Trail of Bits Algorand "Not So Smart Contracts" 11-pattern security framework.
- **Dynamic & Adversarial Simulation:** 934+ test cases running on localnet, testnet, and mock harness environments, including adversarial pool simulation (`contracts/malicious_pool.py`) and real opcode fuzzing.

## 3. Severity Classification Standards

| Severity | Definition |
|----------|------------|
| **Critical** | Direct theft of user funds, contract insolvency, or complete loss of protocol funds without prerequisites. |
| **High** | Conditional loss of user or protocol funds, major denial-of-service, or broken core security invariants. |
| **Medium** | Economic leakage, unexpected execution drift, resource griefing, or unauthenticated parameters with bounded impact. |
| **Low** | Code hygiene, non-critical parameter checks, diagnostic ambiguity, or minor design inconsistencies. |
| **Informational** | Optimization opportunities, architectural suggestions, or documentation clarity. |

## 4. Residual Risks & Operational Assumptions

1. **Quote Signer Key Integrity:** The quote signer key signs the slippage floor note. If this key is compromised, an attacker could sign sub-optimal floors for user trades. Mitigation: Immediate key rotation via `set_quote_signer`.
2. **External AMM Upgrades:** If an external AMM (e.g., Pact MWPT) upgrades its factory creator address on-chain, the router will refuse routes through the new factory until updated. This is a deliberate fail-closed security design.
3. **Admin Key Centralization:** The admin key controls protocol fees (capped at 1%) and treasury conversion parameters. Mitigation: Recommended cold storage or multi-signature custody.
